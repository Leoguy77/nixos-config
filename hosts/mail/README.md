# hosts/mail — mail.lsinfra.de (netcup VPS pico G11s)

Encrypted-root NixOS mail server: **Stalwart** (SMTP/IMAP/JMAP/ManageSieve) +
**Bulwark** webmail, both from the upstream containers, behind an nginx TLS
front that routes by SNI.

```
                :443 (TCP)                    ┌──────────────────────────┐
  Internet ─────────────────► nginx _stream_ ─┤ SNI webmail. → :8445     │─► nginx http ─► bulwark :3000
                :80  ───────► nginx http      └ SNI mail.    → :8443 ─────┘─► stalwart :443 (own TLS)
                :25 :465 :587 :143 :993 :4190 ─────────────────────────────► stalwart
```

Why the split: Stalwart holds its certificate in its own data store and renews
it with ACME/TLS-ALPN-01, which must arrive on port 443 untouched. nginx
therefore only *passes through* TLS for `mail.lsinfra.de`, and terminates TLS
itself for `webmail.lsinfra.de` (HTTP-01, webroot). One ACME client per
hostname, no fight over `/.well-known/`.

|---|---|---|

| IPv6 `2a03:4000:37:c32:6860:64ff:fe3b:ddb0/64`, gw `fe80::1` onlink | same | ✅ confirmed (`ip -6 route`) |
| Disk device `/dev/vda` | `--disk main <dev>` | ✅ confirmed from `lsblk` |

## Prerequisites

1. **netcup CCP**
   - Enable **UEFI boot** for the server (otherwise systemd-boot finds no ESP).
   - Set **rDNS/PTR** for the IPv4 address *and* the IPv6 address to
     `mail.lsinfra.de`. Mail that leaves without matching rDNS is rejected by
     most receivers.
   - No firewall/port blocking on 25/80/443/465/587/993/4190.
2. **DNS for lsinfra.de** — before the first start:

   | Name | Type | Value |
   |---|---|---|
   | `mail` | A | `91.132.147.216` |
   | `mail` | AAAA | `2a03:4000:37:c32:6860:64ff:fe3b:ddb0` |
   | `webmail` | A / AAAA | same |
   | `lsinfra.de` | MX 10 | `mail.lsinfra.de` |
   | `lsinfra.de` | TXT | `v=spf1 mx -all` |
   | `_dmarc` | TXT | `v=DMARC1; p=quarantine; rua=mailto:postmaster@lsinfra.de` |

   DKIM (`_dkim._domainkey`) is generated by Stalwart — publish it in step 6.
   Do **not** publish MTA-STS/TLSA yet.
3. **A machine with Nix** for `nixos-anywhere` (kirito/surface).
4. **SSH key** already in the repo config (the `Github` ed25519 key at
   `modules.server.adminKeys`). Add more keys there if you need them.

## Install

⚠ This wipes `/dev/vda` (currently an unencrypted 3-partition install).

```bash
# 1. Exercise the disk layout in a throwaway VM first (no real disk touched).
VM_TEST=1 scripts/deploy.sh mail root@91.132.147.216 /dev/vda

# 2. Deploy. Prompts for the LUKS passphrase (used at every boot).
scripts/deploy.sh mail root@91.132.147.216 /dev/vda

# Connecting as a non-root user with password-less sudo works too:
#   scripts/deploy.sh mail leoguy77@91.132.147.216 /dev/vda
```

`scripts/deploy.sh` is the general installer for every host of this flake
(`scripts/deploy.sh <host> <user@address> [disk]`); for this one it wraps:

```bash
nixos-anywhere \
  --flake "path:$PWD#mail" \
  --target-host root@91.132.147.216 \
  --disk main /dev/vda \
  --disk-encryption-keys /tmp/luks-password /tmp/luks-password
```

It uses `path:` rather than the default `git+file:` because git flakes copy only
tracked files — the gitignored bootstrap key would otherwise be missing from the
build.

The disk layout is **imported by the host** (`inputs.disko.nixosModules.disko` +
`modules/disko/luks-btrfs-server.nix`), which is why `--disk main` can override
`disko.devices.disk.main.device`. There is no `--disko` flag. No
`--generate-hardware-config` either: the hardware file is committed and kept
free of `fileSystems`, which disko now owns — the script refuses to run if it
finds `fileSystems` there.

## Initrd SSH: tailnet only, never public

The initrd runs `tailscaled` (state on the ESP, see below) and joins the tailnet
as **`mail-initrd`** before the disk is unlocked. sshd then binds to the address
tailscaled handed out — **only** that address:

```
initrd-sshd: listening only on 100.x.y.z:2222
```

Nothing listens on `91.132.147.216` during stage 1. If tailscale does not come
up, the bind script exits non-zero (`Restart=` retries) and sshd never starts: it
fails closed rather than falling back to the public interface.

### No expiring credential (this is the point)

The node identity lives in **`/run/initrd-boot/tailscale-initrd.state`** on the
ESP — unencrypted, so it is readable before the root is unlocked. Consequences:

| | |
|---|---|
| Auth key needed | only to bootstrap the *first* join |
| Auth key expires | irrelevant — not used after boot 1 |
| Node identity | stable (same name, same 100.x address every boot) |
| Key expiry | disable it once for this node (below) and it never re-auths |

That is the answer to “can it not expire”: a Tailscale **auth key cannot exceed
90 days** (hard limit), but a **node** does not need one once its state is
persisted. In the admin console → Machines → `mail-initrd` → **Disable key
expiry** (servers are the documented case for this).

### Bootstrap the first join — nothing to edit

This is a **default for every server host**: `modules.server` turns on
`modules.initrdTailscale`, and the module looks for its bootstrap key at the
conventional path `secrets/tailscale-initrd-<hostname>.authkey` (gitignored).
There is no option to toggle and no file to place by hand —
`scripts/deploy.sh` derives it from sops and deletes it again afterwards.

The one thing to do **once**: store the key in the existing sops file.

```bash
sops secrets/secrets.sops.yaml
# add:  tailscale_initrd_authkey: tskey-auth-…
```

Get the value from <https://login.tailscale.com/admin/settings/keys>:

| Setting | Value |
|---|---|
| Reusable | **off** |
| Ephemeral | **off** (the identity is meant to persist now) |
| Pre-approved | **on** |
| Expiry | 7 days is plenty — it only bootstraps the first boot |

Because the key lives in sops and not in git, and because GitHub builds cannot
derive it, the initrd produced by `autoUpgrade` carries **no** credential — which
is the desired steady state. The persisted node state makes that harmless.

If sops has no such key, `deploy.sh` says so and asks before continuing: the
install still works, but the first boot can only be unlocked on the netcup
console (there is no shell in stage 1 to run `tailscale up` in), and the initrd
will never join the tailnet until a key exists.

### Unlock

```bash
ssh -p 2222 root@mail-initrd      # -p 2222; the node name is the initrd's
# in that session:
systemd-tty-ask-password-agent --watch
```

The initrd host key is the one committed at `hosts/mail/initrd-ssh/`, so the
fingerprint is stable across reboots — no `accept-new` needed.

Fallback if the tailnet join failed: netcup CCP → **Console (VNC)**.

### Why not sops here?

A sops secret has to be decrypted by something, and that something has to run in
the initrd — i.e. its key would also sit on the unencrypted `/boot`. That is the
same exposure as the secret itself, one indirection longer. sops is the right
tool for stage-2 secrets (restic password, anything Stalwart needs), which is why
`modules.sops.enable` stays off only until the host key is in `.sops.yaml`.

### Updates

`system.autoUpgrade` stays **on** for `mail`: nothing secret is needed to build
this host, because the initrd node state lives on the machine itself. The nightly
GitHub rebuild also removes the bootstrap key from the initrd image incidentally
(GitHub cannot see the gitignored file), which is exactly what you want.

Manual rebuild from the workstation:

```bash
nixos-rebuild switch --flake .#mail --target-host root@91.132.147.216 --use-remote-sudo
```

Once stage 2 is up, the normal system joins as **`mail`** (separate node, own
state on the encrypted root):

```bash
ssh root@91.132.147.216 'tailscale up --ssh --accept-dns=false'
```

## First-run configuration (once, interactive)

Stalwart starts in **bootstrap mode**: no listeners, one plain HTTP port on
`:8080`, reachable on loopback only. Tunnel it:

```bash
ssh -L 8081:127.0.0.1:8081 root@mail-initrd
# browser: http://127.0.0.1:8081
```

5. In the setup wizard:
   - server hostname `mail.lsinfra.de`, data store RocksDB (default),
   - admin account + password,
   - domain `lsinfra.de`,
   - **no DNS provider** → the wizard uses ACME/TLS-ALPN-01, which works
     through the nginx SNI passthrough. If it fails, the passthrough is
     misconfigured; check `systemctl status nginx` and
     `podman logs stalwart`.
   - Remove `STALWART_RECOVERY_ADMIN` from the environment afterwards if you set
     one (it is a full-access credential).

6. Domain settings → publish **DKIM** TXT record, keep SPF/DMARC as above.
   Then send a test mail to <https://www.mail-tester.com> and to a Gmail
   address, and check that both directions work over IPv4 *and* IPv6.

7. HTTP access control (Stalwart → Settings → HTTP): allow the origin
   `https://webmail.lsinfra.de`, otherwise the browser's JMAP requests from
   Bulwark are rejected as cross-origin.

8. Bulwark: the setup token is printed in the container log:

   ```bash
   ssh root@91.132.147.216 journalctl -u podman-bulwark -n 100 | grep -i setup
   ```

   Open <https://webmail.lsinfra.de>, paste the token, finish the wizard.
   `JMAP_SERVER_URL` is already set to `https://mail.lsinfra.de`.

## Then: authorise the host for sops

`modules.sops.enable = false` in `hosts/mail/default.nix` until this is done —
otherwise activation fails because the machine cannot decrypt the shared file.

```bash
# on the server
ssh-to-age < /etc/ssh/ssh_host_ed25519_key.pub
# on your workstation: add that age1... to .sops.yaml, then
sops updatekeys secrets/secrets.sops.yaml
# set modules.sops.enable = true; git push
```

## Operating notes

- **Updates**: `system.autoUpgrade` rebuilds daily from GitHub with
  `allowReboot = false`, because a reboot needs the passphrase.
  Manual: `nixos-rebuild switch --flake github:Leoguy77/nixos-config#mail`.
- **RAM**: 1 GB total. Stalwart is capped at 640 MB, Bulwark at 256 MB, and
  zram gives compressed swap. Watch `zramctl` / `podman stats`; Stalwart's
  search index is the hungry part, so keep "index full text" off if memory
  gets tight.
- **Disk**: 30 GB, `/var` is a separate subvolume with `nodatacow` (RocksDB).
  Check `btrfs filesystem usage /`.
- **Backups**: `modules.backup` (restic) covers `/var/lib/stalwart` and
  `/var/lib/bulwark`; set `modules.backup.repository` to an off-site target
  once you have one.
- **Ports**: `nft list ruleset`. Only 22, 25, 80, 143, 443, 465, 587, 993,
  4190 are open, plus the tailnet interface.
- **Stalwart version pinning**: `modules.mail.stalwartImage` is on `v1.0`. A
  1.0 server cannot open a 0.16 data store, so never move to `latest` casually.
